## Codebase Patterns
- CreativeBridge uses PostgreSQL/Supabase for database with comprehensive RLS policies
- All migrations follow pattern: CREATE TABLE IF NOT EXISTS, comprehensive indexes, RLS policies, helper functions
- Migration files include inline documentation with COMMENT ON TABLE/COLUMN statements
- Always use SECURITY DEFINER for helper functions that need elevated privileges
- Database functions use explicit parameter naming (p_parameter_name) for clarity
- JSONB is preferred for flexible metadata storage with GIN indexes for queries
- All user-owned data must have RLS policies checking auth.uid() = user_id
- Indexes follow naming convention: idx_tablename_column1_column2
- Constraints use descriptive names and CHECK constraints for data validation
- Rollback procedures are documented in comments at end of migration files

**Learnings for future iterations:**
- **LLM structured output**: Use low temperature (0.3) with explicit JSON schema in system prompt for consistent structured extraction. Always strip markdown code blocks from responses.
- **Normalization is critical**: Singular form and lowercase ensure semantic matching works (e.g., "Keys" and "key" match). Simple heuristics work well: remove -s/-es/-ies for plurals, -ing/-ed for verbs.
- **Fallback is essential**: Never let service completely fail - regex-based keyword extraction provides degraded but functional behavior when LLM unavailable.
- **Retry strategy**: Exponential backoff with 3 retries handles transient API failures. Don't retry on auth errors (fail fast). Use 1s base delay to avoid hammering API.
- **Story truncation**: Limit input to 4000 chars (~1000 tokens) to avoid token limit errors and reduce API costs.
- **Test mocking patterns**: Mock `openaiClient.isConfigured()` and `generateStoryCompletion()` separately - allows testing both success and failure paths cleanly.
- **Element types match database**: Ensure extracted element types (character, setting, object, plot_pattern) match the database enum for story_elements.element_type.

**Technical decisions:**
- Used GPT-4 Turbo instead of GPT-3.5: Better at following structured output instructions, worth the slightly higher cost
- JSON parsing with markdown stripping: LLM sometimes adds ```json code blocks despite instructions - handle gracefully
- Fallback uses keyword matching: Simple but effective for common story elements (animals, settings, magical objects)
- Service never throws on extraction failure: Falls back to empty arrays rather than crashing story generation flow
- Normalization happens after LLM extraction: Allows LLM to use natural language, then we normalize for consistency
