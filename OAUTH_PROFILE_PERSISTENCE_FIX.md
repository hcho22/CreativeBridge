# OAuth Profile Persistence Bug Fix

## Problem Summary

After signing in via Google OAuth, user profile information (username, display name) was appearing correctly on the Home screen but showing as "Not set" when navigating to the Profile or Settings screens.

## Root Cause Analysis

### The Bug

The issue was in the `fetchUserProfile` function in [AuthContext.tsx](src/context/AuthContext.tsx). This function was querying the `user_profiles` table by the `id` field for ALL users, including OAuth users.

```typescript
// OLD CODE (BUG):
const { data: existingProfile, error } = await supabase
  .from('user_profiles')
  .select('*')
  .eq('id', userId) // ❌ This fails for OAuth users
  .single();
```

### Why It Failed

OAuth users have a different ID structure than email/password users:

- **OAuth users**: The `user.id` is the Clerk user ID (e.g., `user_37r7rBfZHFMDzsY1y2YobJiC1mW`)
- **Regular users**: The `user.id` is the Supabase auth UUID

In the database schema, OAuth user profiles are stored differently:

- `user_profiles.id` = The profile's UUID (generated by Supabase)
- `user_profiles.clerk_user_id` = The Clerk user ID (e.g., `user_37r...`)

When `fetchUserProfile` tried to query by `id` field using the Clerk user ID, it couldn't find the profile because the Clerk user ID is stored in the `clerk_user_id` field, not the `id` field.

### When The Bug Occurred

1. **Initial OAuth Login**: Profile loaded correctly because `syncClerkWithSupabase` fetched the profile by `clerk_user_id` and stored it in context
2. **Navigation to Profile/Settings Screen**: These screens call `refreshProfile()` → `fetchUserProfile(user.id)` → query fails because it searches `id` field with a Clerk user ID value

## The Fix

### Solution

Modified `fetchUserProfile` to detect Clerk user IDs (which always start with `user_`) and query the correct field:

```typescript
// NEW CODE (FIX):
const isClerkUserId = userId.startsWith('user_');

if (isClerkUserId) {
  // Query by clerk_user_id for OAuth users
  const { data: profiles, error: clerkError } = await supabase
    .from('user_profiles')
    .select('*')
    .eq('clerk_user_id', userId) // ✅ Correct field for OAuth users
    .limit(1);

  const existingProfile = profiles && profiles.length > 0 ? profiles[0] : null;
  // ... handle result
} else {
  // Query by id for regular email/password users
  const { data: existingProfile, error } = await supabase
    .from('user_profiles')
    .select('*')
    .eq('id', userId) // ✅ Correct field for regular users
    .single();
  // ... handle result
}
```

### How It Works

1. **ID Detection**: Check if the user ID starts with `user_` (Clerk's consistent pattern)
2. **Conditional Query**:
   - OAuth users → query `clerk_user_id` field
   - Regular users → query `id` field
3. **Result Handling**: Handle both query patterns appropriately

## Related Code Flow

### Profile Loading Chain

1. **Initial Login**: `signInWithGoogle()` → `syncClerkWithSupabase()` → profile loaded by `clerk_user_id`
2. **Screen Navigation**: `ProfileScreen` or `SettingsScreen` → `refreshProfile()` → `fetchUserProfile(user.id)` → NOW queries by correct field

### Why This Affects Multiple Screens

Both ProfileScreen and SettingsScreen depend on `userProfile` from AuthContext:

- **ProfileScreen**: Calls `refreshProfile()` on mount (line 38)
- **SettingsScreen**: Reads `userProfile` state directly (lines 28, 195-196, 201-202)

When `fetchUserProfile` failed, it returned `null`, which cleared the `userProfile` state, causing both screens to show "Not set".

## Prevention

### Design Pattern

The fix follows a pattern that should be used throughout the codebase:

- Always check if a user ID is a Clerk user ID before querying
- Use `userId.startsWith('user_')` to detect OAuth users
- Query by `clerk_user_id` for OAuth users, `id` for regular users

### Future Considerations

1. Consider creating a helper function: `isClerkUserId(id: string): boolean`
2. Consider creating a helper function: `queryProfileById(userId: string)` that encapsulates this logic
3. Add similar checks to any other functions that query user profiles

## Database Schema Context

### user_profiles Table Structure

```sql
CREATE TABLE user_profiles (
  id UUID PRIMARY KEY,                    -- Supabase auth UUID
  clerk_user_id TEXT UNIQUE,              -- Clerk user ID (for OAuth)
  username TEXT NOT NULL UNIQUE,
  display_name TEXT,
  preferred_grade_level grade_level_type,
  -- ... other fields
);
```

### Key Points

- `id`: Always a UUID, matches Supabase auth user ID for email/password users
- `clerk_user_id`: Only populated for OAuth users, matches Clerk user ID (format: `user_xxxxx`)
- For OAuth users: `id` ≠ `clerk_user_id` (they are different values)
- For regular users: `id` = Supabase auth UUID, `clerk_user_id` = NULL
